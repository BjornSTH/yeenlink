# YeenLink — техническая спецификация и фазы разработки

Oct 2, 2026 · @Gori huma

## Обзор

YeenLink — self-hosted мессенджер с текстом, голосом и стримами, который ставится одной командой на VPS за \~200 ₽ (1 ядро, 1–2 ГБ ОЗУ) и держит 100+ человек. Сервер пишется на Go, клиент на Flutter (Windows, Linux, Android, затем macOS), голос и видео идут через LiveKit.

Чем отличается от Discord и альтернатив:

- **Нет центра.** Каждое сообщество держит свой сервер; блокировка одного адреса не отрезает людей, клиент сам переходит на запасной.
- **Профиль у пользователя.** Личность — это пара ключей Ed25519 на устройстве, профиль и стена подписаны ей и переезжают между серверами без регистрации.
- **Лёгкость.** Один бинарник сервера, SQLite в малом режиме, клиент без Electron.
- **Честный интерфейс.** Пользователь видит, через какой адрес подключён, что увидит сервер и почему недоступно качество выше лимита.

**Границы MVP:** текстовые каналы, личные сообщения, голосовые каналы, демонстрация экрана с ПК, роли и права, приглашения, состояния соединения, онбординг с seed-фразой, привязка устройств, настройки пользователя и сервера, режим стримера. **Вторая волна:** каталог серверов, стены и лента, светлая тема в коде. **Вне MVP:** комментарии к постам, сквозное шифрование, демонстрация экрана с Android, кластерный режим сервера.

Макеты всех экранов: [холст YeenLink](https://claude.ai/artifact/KkMUR6Wruy2sGVYAgRDryQ). Цвета, шрифты, отступы и компоненты: [дизайн-система YeenLink](https://claude.ai/artifact/N1zVHZUcfEBrRW1ru1Kkf8).

## Архитектура и стек

Сервер — один Go-бинарник со встроенным LiveKit рядом; клиент на Flutter держит отдельное соединение с каждым своим сервером, а каталог — необязательный отдельный сервис.

&#91;embedded content: архитектура · клиент, сервер, каталог\]

Чат и события идут по WebSocket в CBOR, вложения — по HTTPS по хешу, голос и стрим — по UDP 7882 через LiveKit; сервер сам регистрируется в каталоге, если админ сделал его видимым.

| Слой | Выбор | Почему |
| --- | --- | --- |
| Сервер | Go, один бинарник под systemd | Тысячи соединений на одном ядре, лёгкая установка |
| Хранилище | SQLite (WAL, FTS5); PostgreSQL — позже для кластера | Не нужен отдельный процесс на слабом VPS |
| Медиа | LiveKit SFU, VP9/AV1 с временными слоями, Opus | Без перекодирования, есть Flutter SDK |
| Сертификаты | certmagic в самом сервере | Не нужен nginx или Caddy |
| Клиент | Flutter: Windows, Linux, Android, затем macOS | Один код, официальный LiveKit SDK, 20–40 МБ |
| Хранилище клиента | `drift` (SQLite), системное хранилище ключей | Офлайн-очередь и история |
| Кодек | CBOR везде, JSON — отладочный режим | Подписанные конверты уже бинарные |
| Криптография | Ed25519, BIP39, SHA-256 (`crypto/ed25519`, пакет `cryptography`) | Стандартные библиотеки обоих языков |

## Идентичность и ключи

Личность пользователя — главный ключ Ed25519, выведенный из seed-фразы BIP39; для повседневной работы каждое устройство использует свой ключ, заверенный главным.

### Ключи

| Ключ | Откуда | Где хранится | Зачем |
| --- | --- | --- | --- |
| Главный (master) | 12 слов BIP39 (английский список, без пароля) → seed 64 байта (PBKDF2-HMAC-SHA512) → SLIP-0010 Ed25519, путь m/22860'/0'/0' | Хранится энтропия фразы: XChaCha20-Poly1305 под ключом Argon2id от PIN (6 цифр), блоб — в системном хранилище (Android Keystore, Диспетчер учётных данных Windows (DPAPI), libsecret) | Подписать сертификат устройства, отзыв, профиль, смену ключа |
| Ключ устройства | Случайный, создаётся на устройстве | Системное хранилище, без PIN | Вход на серверы, подпись сообщений и постов |
| Хеш следующего главного ключа | Тот же путь с индексом 1 (m/22860'/0'/1'); в профиле хранится SHA-256 его публичного ключа | Поле `next_key_hash` в профиле | Защита от угона фразы во второй версии (предварительная ротация); в MVP только хранится |
| Ключ сервера | Создаётся при первом запуске сервера | Файл на сервере | Подпись приглашений, списка адресов, ответов на challenge |

Отпечаток для показа людям: первые 8 байт SHA-256 от публичного ключа, четыре группы по 4 hex-символа (`A0D2·5F11·8C3E·07B9`), в карточках — первые две группы.

### Вход на сервер (challenge–response)

1. Клиент открывает WebSocket и шлёт `hello {device_pub, master_pub, device_cert}`.
2. Сервер отвечает `challenge {nonce 32 байта, server_pub, ts}`.
3. Клиент подписывает ключом устройства байты `"yl-auth-v1" | nonce | server_pub | ts` и шлёт `auth {sig}`.
4. Сервер проверяет подпись, сертификат устройства (подписан master, не отозван) и выдаёт сессию.

`server_pub` внутри подписи не даёт поддельному серверу переслать challenge настоящему и войти от имени пользователя.

### Устройства и потеря

| Ситуация | Что делает пользователь | Что происходит в системе |
| --- | --- | --- |
| Новое устройство, старое под рукой | Старое: «Привязать по QR» → новое сканирует → старое подтверждает «Разрешить вход» | Новое создаёт ключ устройства; старое (разблокировав master PIN-кодом) подписывает сертификат; master передаётся зашифрованным напрямую между устройствами |
| Потерян ПК, телефон привязан | Телефон: «Безопасность → Устройства → Отвязать» + PIN | Телефон подписывает отзыв ключа ПК и новый список `devices` (`seq+1`); при подключении список уходит на все серверы, они перестают пускать ключ ПК |
| Потерян ПК, телефон не привязан | Телефон: «У меня уже есть профиль» → 12 слов | Фраза восстанавливает master, телефон создаёт свой ключ и отзывает ПК |
| Нет устройств и нет фразы | Восстановление из зашифрованной копии на родном сервере по паролю (если включено) | Иначе личность утеряна; админ конкретного сервера может вручную перенести роли на новый ключ на своём сервере |
| Утекла сама фраза | В MVP — только создать новую личность | Вторая версия: смена главного ключа разрешена только владельцу ключа, чей хеш записан в `next_key_hash` |

PIN-код нужен для показа фразы, привязки и отвязки устройств; без PIN главный ключ не расшифровывается. Код привязки по QR одноразовый, живёт 2 минуты; без подтверждения на старом устройстве ключ не передаётся.

## Форматы данных

Всё подписанное передаётся конвертом «байты + подпись»: payload кодируется в CBOR один раз и дальше никогда не пересобирается, поэтому канонизация не нужна.

### Подписанный конверт

```
Signed = {
  t:    text      ; тип: "profile" | "post" | "device_cert" | "revoke" | "devices" | "addresses" | "invite"
  p:    bytes     ; CBOR-байты payload, хранятся и пересылаются как есть
  k:    bytes(32) ; публичный ключ подписавшего
  s:    bytes(64) ; Ed25519( "yl-v1" | t | p )
}
```

Проверка: тип `t` входит в подписываемые байты, поэтому подпись поста нельзя выдать за подпись профиля.

Склейка `"yl-v1" | t | p` идёт без разделителя, поэтому ни один тип `t` не может быть началом другого; каждый новый тип проверяется на это тестом.

### Профиль (`t = "profile"`, подписывает master)

| Поле | Тип | Ограничение / смысл |
| --- | --- | --- |
| `v` | uint | Версия формата, сейчас 1 |
| `master` | bytes(32) | Публичный главный ключ |
| `seq` | uint | Растёт с каждой правкой; сервер принимает только больший |
| `name` | text | 1–32 кодовые точки после NFC и обрезки пробелов; управляющие символы и символы направления текста запрещены |
| `about` | text | ≤ 300 кодовых точек, те же правила, что у name |
| `avatar` | `{sha256, mime, size}` | WebP/PNG ≤ 512 КБ, по хешу |
| `banner` | `{sha256, mime, size}` или `banner_color` | Картинка ≤ 1 МБ либо banner\_color = имя токена banner-1…5 (неизвестное → banner-1) |
| `wall` | bool | Разрешена ли стена; по умолчанию true |
| `next_key_hash` | bytes(32) | SHA-256 следующего главного ключа (на будущее) |
| `home` | text? | Адрес родного сервера-зеркала, если включён |
| `updated` | uint | Unix-время, мс |

Картинки адресуются хешем: клиент шлёт профиль, сервер запрашивает `blob/<sha256>`, только если такого файла у него нет.

### Пост на стене (`t = "post"`, подписывает ключ устройства)

`{v, id (ULID), author_master, text ≤ 4000, media: [{sha256, mime, size}] ≤ 4, servers: [server_pub], created}`. Сервер принимает пост, только если его `server_pub` есть в `servers`, стены включены и не превышен лимит постов на человека. Реакции — отдельные мелкие события, не подписываются master.

### Сертификат устройства, отзыв, список устройств

- `device_cert` (подписывает master): `{device_pub, name, platform, created}`.
- `revoke` (подписывает master): `{device_pub, reason, at}`.
- `devices` (подписывает master): `{seq, active: [device_pub], revoked: [device_pub]}` — клиент отправляет актуальный список на каждый свой сервер при подключении.

В `device_cert` поле `platform` — `windows`, `linux`, `android` или `macos`; имя по умолчанию — «Компьютер · ОС» или «Телефон · модель», а не имя компьютера: список устройств видят серверы, а имя компьютера часто содержит настоящее имя. Устройство, восстановленное по фразе, создаёт только свой `device_cert`; новый список `devices` (`seq+1`) оно отправляет при первом подключении к серверу, когда узнаёт текущий `seq` (фаза 2).

### Приглашение (`t = "invite"`, подписывает сервер)

```
Invite = {
  v:        1
  server:   bytes(32)          ; ключ сервера
  name:     text               ; название, для экрана «Вас пригласили»
  addrs:    [ {h: text, p: uint, kind: "main"|"backup"|"mirror"} ]
  secret:   bytes(16)          ; 128 бит, по нему сервер находит приглашение
  exp:      uint?              ; срок, unix-время в мс, как все времена
  uses:     uint?              ; лимит использований (сервер считает сам)
  approve:  bool               ; нужна ли заявка
}
```

Ссылка: `yl://i/<base64url(Signed)>` — около 250–300 символов, без короткого кода для диктовки. Веб-вариант `https://yeenlink.app/i#<то же>`: всё после `#` браузер не отправляет на сайт. Клиент проверяет подпись `server`, а при подключении — что сервер владеет этим ключом.

### Список адресов (`t = "addresses"`, подписывает сервер)

`{seq, addrs: [...] }` — тот же формат, что в приглашении. Сервер присылает его при каждом входе; клиент заменяет локальный список, если `seq` больше.

## Протокол клиент–сервер

Один WebSocket на сервер с кадрами CBOR; файлы — обычным HTTP; голос и видео — LiveKit по токену, который выдаёт наш сервер.

### Кадр

```
Frame = { op: text, id: uint?, d: any, e: {code: text, msg: text}? }
```

- Запрос клиента несёт `id`, ответ сервера — тот же `id` и либо `d`, либо `e`.
- События сервера идут без `id`.
- Отладочный режим: сервер с флагом `--codec=json` говорит тем же кадром в JSON; утилита `yl-decode` переводит CBOR-кадры из логов в читаемый JSON.
- Сжатие: `permessage-deflate`.

Общие правила профиля CBOR (Go и Dart одинаково):

- Все времена — unix-время в **миллисекундах**, без исключений.
- Целые — в диапазоне int64: поля, описанные как `uint`, на разборе отвергаются, если значение отрицательное или не влезает в int64 (Dart хранит целые как 64-битные со знаком).
- Байты в отладочном JSON — объект `{"$bytes": "<base64url без =>"}`; подробно — `spec/json-debug.md` в репозитории.
- Кодирование детерминированное (порядок ключей по RFC 8949 §4.2.1, длины с явным счётчиком); разбор строгий: дубликаты ключей, теги, длины без счётчика и превышение глубины — ошибка.

### Операции (MVP)

| Группа | Запросы клиента | События сервера |
| --- | --- | --- |
| Вход | `hello`, `auth`, `resume` | `challenge`, `ready {server, me, channels, roles, perms, addresses}` |
| Профиль | `profile.push`, `blob.need?` | `member.update`, `blob.want` |
| Сообщения | `msg.send {client_id}`, `msg.edit`, `msg.delete`, `msg.history`, `react.toggle` | `msg.new`, `msg.update`, `msg.gone`, `react.update`, `typing` |
| Каналы | `channel.create/update/delete/move` | `channel.update` |
| Участники | `member.kick`, `member.ban`, `member.admit`, `member.roles` | `member.join/leave/update`, `presence` |
| Роли | `role.create/update/delete/move` | `role.update`, `perms.update` (готовые права по каналам) |
| Приглашения | `invite.create/revoke/list`, `invite.redeem` | `invite.update` |
| Голос | `voice.join {channel}`, `voice.leave`, `stream.start {preset, res, fps}`, `stream.stop` | `voice.token {livekit_url, jwt}`, `voice.state`, `stream.limit`, `stream.warn {level}` |
| Стены | `post.push`, `post.hide`, `feed.get` | `post.new`, `post.hidden` |
| Сервер | `server.settings.get/set`, `admin.claim {token}` | `server.update`, `addresses` |
| Устройства | `devices.push`, `revoke.push` | — |

### HTTP

- `PUT /blob/<sha256>` — загрузка вложения или аватара после `blob.want`; сервер проверяет хеш и лимиты размера.
- `GET /blob/<sha256>` — скачивание, с авторизацией по токену сессии.
- `GET /.well-known/yeenlink` — ключ сервера, версия, имя: так клиент проверяет адрес до входа.

Сессия переживает обрыв: `resume {session, last_event}` возвращает пропущенные события, если прошло меньше 5 минут; иначе клиент заново делает `hello`.

## Роли и права

Права — битовая маска `uint64` на роль плюс переопределения на канал; итоговые права считает только сервер и присылает клиенту готовыми (`perms.update`), клиент лишь прячет кнопки.

### Биты (MVP)

| Бит | Право | Группа в админке |
| --- | --- | --- |
| 0 | `MANAGE_SERVER` — название, лимиты, адреса | Сервер |
| 1 | `MANAGE_ROLES` — только роли ниже своей | Сервер |
| 2 | `MANAGE_CHANNELS` | Сервер |
| 3 | `CREATE_INVITE` | Сервер |
| 4 | `KICK` | Участники |
| 5 | `BAN` (по ключу) | Участники |
| 6 | `ADMIT` — одобрять новичков | Участники |
| 7 | `VIEW_CHANNEL` | Сообщения |
| 8 | `SEND_MESSAGES` | Сообщения |
| 9 | `ATTACH_FILES` | Сообщения |
| 10 | `MANAGE_MESSAGES` — удалять чужие | Сообщения |
| 11 | `HIDE_POSTS` — скрывать посты на стенах | Сообщения |
| 12 | `CONNECT` | Голос |
| 13 | `SPEAK` | Голос |
| 14 | `STREAM` | Голос |
| 15 | `CAMERA` | Голос |
| 16 | `MOVE_MEMBERS` | Голос |
| 63 | `OWNER` — все права, не снимается | — |

### Расчёт для канала

1. Владелец → все биты, конец.
2. База = OR масок всех ролей участника (включая неявную роль «все»).
3. Переопределения канала для роли «все»: `base &^ deny | allow`.
4. Затем для ролей участника: сначала все `deny`, потом все `allow`.
5. Затем персональное переопределение участника.
6. Нет `VIEW_CHANNEL` → канал скрыт целиком.

Иерархия: роли упорядочены по позиции; управлять можно только ролями и людьми ниже своей самой высокой роли. Права голоса превращаются в разрешения токена LiveKit: `canPublish` (SPEAK), `canPublishSources` с экраном (STREAM) и камерой (CAMERA), `canSubscribe` (CONNECT).

### Владелец и ключ администратора

Владельцем становится тот, кто установил сервер, по одноразовому ключу — как привилегированный ключ в TeamSpeak.

1. Первый запуск: сервер создаёт `ylat_<32 байта base62>`, **один раз** печатает его в консоль и кладёт в файл с правами `0600`; в журнал не пишет.
2. Пользователь подключается и видит «У сервера пока нет владельца» → «Ввести ключ администратора».
3. `admin.claim {token}`: сервер сравнивает хеш, назначает `OWNER` публичному главному ключу пользователя и стирает ключ.
4. Новый ключ — только из консоли сервера: `ylsrv admin-token`. Доступ к консоли и есть доказательство владения; это же спасает админа, потерявшего свою личность.
5. Попытки `admin.claim` ограничены: 5 в минуту на адрес.

Баны привязаны к главному ключу. Защита от обхода новым ключом — серверные правила: одобрение новичков, капча, «новые ключи только читают первые сутки».

## Соединение и устойчивость

Клиент держит для каждого сервера список адресов и сам переключается между ними; доверие держится на ключе сервера, а не на сертификате, поэтому работают и самоподписанные сертификаты, и зеркала.

### Переключение адресов

1. Обрыв → состояние «переподключаюсь» (янтарная полоса) и задержка 1, 2, 4… до 30 с со случайным разбросом ±30%, чтобы клиенты не ударили по серверу одновременно.
2. Сначала последний рабочий адрес; не ответил за 1,5 с — параллельно остальные со сдвигом 250 мс (как happy eyeballs).
3. Победитель — первый, кто прошёл TLS и `GET /.well-known/yeenlink` с ожидаемым `server_pub`, а затем challenge.
4. Подключились не к основному → зелёная полоса «работает через запасной адрес»; основной проверяется раз в минуту, при успехе клиент тихо возвращается.
5. Все адреса молчат → красная полоса «сервер недоступен», повтор каждые 10 с и кнопка «Повторить сейчас».
6. Сертификат: если отпечаток TLS не совпадает с закреплённым в приглашении, но `server_pub` верный — вход разрешён; если `server_pub` чужой — соединение рвётся с ошибкой «это не тот сервер».

### Очередь неотправленных

- Локальная SQLite (`drift`), таблица `outbox {client_id ULID, channel, payload, created, state, attempts}`.
- Отправка при подключении в порядке `created` внутри канала; сервер отбрасывает дубли по `client_id`, поэтому повтор безопасен.
- Время сообщения ставит сервер; в ленте до подтверждения сообщение помечено «ожидает отправки».
- Правки и удаления тоже идут через очередь и ссылаются на `client_id`, если серверного id ещё нет.
- Сообщения старше 24 часов не досылаются молча: клиент спрашивает «Отправить сейчас / Удалить».

### Порты

| Порт | Назначение | Обязателен |
| --- | --- | --- |
| TCP 443 или любой | API, WebSocket, веб-клиент, сигнализация LiveKit через прокси по пути `/rtc` | да |
| UDP 7882 | Голос и видео (весь медиатрафик в один порт) | да |
| TCP 7881 | Медиа по TCP, если UDP режется | нет |
| TCP 80 | Выпуск сертификата Let's Encrypt (HTTP-01) | нет |
| TLS 443 (SNI) | TURN для строгих сетей | нет |

Если 443 занят: другой порт в приглашении; работа за существующим nginx/Caddy на поддомене; разделение 443 по SNI через `nginx stream` + `ssl_preread`. Сертификат: Let's Encrypt (HTTP-01, TLS-ALPN-01 или DNS-01 через API регистратора), свой файл или самоподписанный с отпечатком в приглашении. При первом запуске сервер сам проверяет, какие порты свободны, и предлагает вариант.

## Голос, видео и стримы

Голос и видео идут через встроенный LiveKit (SFU, без перекодирования); наш сервер выдаёт токены с правами и жёстко ограничивает битрейт стрима, а при перегрузке канала снижает качество ступенями, прежде чем остановить демонстрацию.

### Голос

- Opus с DTX: в тишине поток почти нулевой, поэтому даже 50 человек в канале — единицы Мбит/с.
- Шумо- и эхоподавление на клиенте; режим рации — клавиша на ПК.
- Плитка говорящего подсвечивается по `ActiveSpeakers` из LiveKit.

### Демонстрация экрана (ПК)

- Выбор: весь экран, окно приложения, камера или карта захвата. На Linux с Wayland список окон показывает системный диалог (xdg-desktop-portal); на Windows и X11 — сетка превью.
- Режим задаёт `contentHint`: «Игра» = `motion` (1080p · 60 по умолчанию, при перегрузке снижается разрешение), «Текст и код» = `detail` (1440p · 30, снижаются кадры).
- Разрешение 720p / 1080p / 1440p, кадры 30 / 60 / 90 / 144.
- 90 и 144 кадров — только при аппаратном кодировщике (NVENC, AMF, Quick Sync); клиент проверяет его при запуске.
- Комбинации тяжелее лимита сервера показываются, но недоступны, с причиной.

### Оценка битрейта (на одного зрителя)

Формула клиента и админки: `4 Мбит/с × k_res × k_fps × k_mode`, где `k_res` = 0,3 / 0,55 / 1 / 1,7 (480p / 720p / 1080p / 1440p), `k_fps` = 1 / 1,5 / 2 / 2,8 (30 / 60 / 90 / 144), `k_mode` = 1 для игры и 0,6 для текста. Это ориентир для интерфейса; реальные значения уточняются нагрузочным тестом (фаза 7).

### Временные слои

Стример кодирует один поток VP9 или AV1 с временными слоями (144 → 72 → 36 кадров); SFU отбрасывает лишние кадры для каждого зрителя без перекодирования. Клиент сообщает частоту своего экрана и тип сети; 60-герцовый монитор получает слой 72, телефон — нижний слой simulcast. Зритель до нажатия «Подключиться к эфиру» не подписан на видео и видит только размытое превью раз в несколько секунд.

### Деградация при перегрузке

Сервер знает пропускную способность канала из настроек админа (100 Мбит/с / 300 Мбит/с / 1 Гбит/с) и следит за исходящим трафиком и процессором.

| Загрузка канала | Действие сервера | Что видят люди |
| --- | --- | --- |
| ≥ 70% | Зрителям на слабых каналах — нижний слой | Почти ничего |
| ≥ 85% | Снижает слой стрима по режиму (игра — разрешение, текст — кадры); новым зрителям — пониженное качество | Стример: янтарная полоса «Сервер на пределе» |
| ≥ 95% дольше 10 с | Останавливает демонстрацию, чтобы не рвался голос | Стример: красная полоса с отсчётом и кнопкой «Снизить до 720p сейчас» |

Голос всегда в приоритете: стрим режется раньше, чем начинают теряться голосовые пакеты.

## Режим стримера

Режим стримера прячет на экране всё, по чему зрители внешнего стрима (Twitch, YouTube) могут найти сервер и устроить набег; работает только на клиенте, сервер о нём не знает.

### Что скрывается

| Что | Как скрывается | Где встречается |
| --- | --- | --- |
| Названия серверов | Заменяются на «Сервер скрыт» | Шапка колонки каналов, заголовки окон, настройки сервера, каталог |
| Иконки и баннеры серверов | Размытие (`blur` 7 px) | Рельса серверов, карточки каталога, приглашение |
| Приглашения и QR | Ссылка не показывается, кнопка «Скопировать» работает; QR скрыт | Создание приглашения, список приглашений |
| Адреса, IP, порты | Заменяются на «скрыто» | Полосы связи, «Адреса и соединение», «Вход по приглашению» |
| Отпечатки ключей и handle | Вместо `имя@сервер · A0D2·5F11` — «скрыто» | Карточка участника, страница профиля, панель пользователя, участники в админке |
| Текст уведомлений | Только «Новое сообщение», без автора и сервера | Системные уведомления |
| Звуки уведомлений | Выключаются (по желанию) | — |

Каналы, сообщения, имена людей и голос остаются как есть: стример показывает то, что происходит, но не то, где это происходит.

**Почему заглушки, а не размытие.** Размытый текст известного шрифта иногда удаётся восстановить, поэтому текстовые идентификаторы заменяются заглушкой целиком, а размываются только картинки. Длина заглушки фиксированная и не повторяет длину оригинала.

### Как включается

1. Автоматически: клиент раз в 10 с проверяет список процессов (OBS, Streamlabs, XSplit и подобные; список в конфиге клиента) и включает режим, пока программа запущена.
2. Горячей клавишей Ctrl + Shift + S или из настроек.
3. Пока режим включён, над списком каналов висит плашка «Режим стримера · найден OBS» с кнопкой «Выкл.»; выключение вручную держится до закрытия OBS, чтобы режим не включился обратно через 10 с.

Все подписи для идентификаторов проходят через одну функцию отображения (`redact(kind, value)`), чтобы новый экран не мог случайно показать адрес или ключ в обход режима; это проверяется тестом, который рендерит экраны с включённым режимом и ищет в дереве виджетов адреса, отпечатки и названия серверов.

## Модули, боты и темы

YeenLink расширяется на трёх уровнях: темы — только данные, боты — внешние программы через API, модули — код в песочнице WebAssembly внутри сервера. Боты и модули получают права так же, как люди, — через роли, поэтому отдельной модели прав для них нет.

| Уровень | Что это | Где работает | Кто ставит | Когда |
| --- | --- | --- | --- | --- |
| Тема | JSON с цветами, без кода | Клиент | Пользователь | Фаза 9 |
| Бот | Отдельная программа с ключом бота | Где угодно, подключается к серверу | Админ создаёт ключ, владелец бота запускает | Фаза 3б |
| Модуль | Файл `.wasm` + манифест | Внутри сервера, в песочнице wazero | Админ сервера | Фаза 10, после MVP |

Плагинов с кодом на стороне клиента нет и не планируется: на клиенте лежат ключи пользователя, и чужой код рядом с ними — слишком большой риск.

### Боты

1. **Личность.** Админ в «Настройки сервера → Боты» создаёт бота: сервер генерирует пару ключей, публичный ключ становится личностью бота, а приватный показывается один раз (как ключ администратора). Профиль бота содержит `bot: true` и главный ключ владельца-человека.
2. **Права.** Бот получает роль «Бот» (или любую другую); всё, что он видит и делает, ограничено этой ролью и переопределениями каналов. Бейдж «БОТ» на сообщениях и в списке участников.
3. **Подключение.** Тот же WebSocket и тот же вход по challenge, что у клиента, но ключом бота. Для Go — SDK в репозитории; протокол открыт, бота можно написать на чём угодно, что умеет CBOR.
4. **Слэш-команды.** Бот регистрирует команды (`/roll`, описание, аргументы); клиент показывает их в автодополнении поля ввода; сервер передаёт вызов боту событием `cmd.invoke`, ответ приходит как обычное сообщение от бота.
5. **Входящие вебхуки.** Самый простой бот без постоянного соединения: адрес вида `https://<сервер>/hook/<секрет>` для отправки сообщений в один канал (уведомления из CI, RSS).
6. **Ограничения.** Не больше 5 сообщений в секунду на канал и 50 на сервер; превышение — ошибка `rate_limited`, а не молчаливая потеря.

Макеты: «Настройки сервера → Боты и вебхуки» (ПК и Android) и автодополнение слэш-команд в поле ввода — команды ботов и встроенные (/me, /streamer) в одном списке с источником справа.

### Модули (WebAssembly)

- **Формат.** Модуль — файл `.wasm` (WASI) и `manifest.json`: имя, версия, автор, запрашиваемые права, события, на которые он подписан, лимиты. Писать можно на TinyGo, Rust, AssemblyScript; SDK сначала для TinyGo.
- **Личность.** Модуль при установке получает свою пару ключей и роль, как бот, — дальше работает та же модель прав.
- **API хоста, версия 1.** События: новое сообщение, вход и выход участника, реакция, вызов слэш-команды, таймер. Функции: отправить или изменить сообщение, ответить на команду, прочитать и записать своё хранилище «ключ–значение» (квота 10 МБ на модуль). Сеть по умолчанию закрыта; доступ к конкретным доменам модуль запрашивает в манифесте, и админ подтверждает его отдельно.
- **Лимиты.** До 32 МБ памяти на модуль, до 50 мс процессорного времени на одно событие; превышение обрывает обработку события. После 5 падений подряд модуль отключается, админ видит причину в журнале.
- **Установка.** Админ загружает файл; сервер показывает хеш модуля и список запрошенных прав, как экран разрешений на Android, и ставит модуль только после подтверждения.

### Темы

- **Формат.** Файл `.yltheme` — JSON: имя, база (`dark` или `light`) и значения цветовых токенов из дизайн-системы. Неизвестные токены игнорируются, отсутствующие берутся из базы.
- **Без кода и без ссылок.** Никаких скриптов, внешних шрифтов и картинок по URL — тема не может следить за пользователем или что-то загрузить.
- **Проверка контраста.** Перед применением клиент проверяет пары текст/фон (`ink`, `muted`, `accent-ink` на фонах `bg-100`…`bg-300`) на 4,5:1; тему с нечитаемым текстом применить нельзя, клиент говорит, какая пара не прошла.
- **Обмен.** Экспорт и импорт файлом в «Настройки → Внешний вид». Сервер может предложить свою тему участникам, но включает её только сам пользователь.

## Лимиты и ресурсы сервера

Минимальная цель — 1 ядро, 1 ГБ ОЗУ, 20 ГБ диска и 100 Мбит/с: 100–200 человек в тексте, 30–50 в голосе и один стрим на 15–20 зрителей; цифры подтверждаются нагрузочным тестом `lk load-test` на реальном VPS.

### Бюджет памяти (1 ГБ)

| Компонент | Ожидаемо |
| --- | --- |
| Debian без лишнего | \~150 МБ |
| Сервер Go + SQLite | 50–100 МБ |
| LiveKit под нагрузкой | 100–200 МБ |
| Запас | \~500 МБ |

Сертификаты получает сам Go-сервер (certmagic), отдельный nginx или Caddy не нужен. Docker — опция для тарифов от 2 ГБ; по умолчанию бинарник под systemd.

### Хранение

- SQLite в режиме WAL, полнотекстовый поиск через FTS5; PostgreSQL — только для будущего кластерного режима.
- Вложения лежат файлами по хешу (`blobs/ab/cd/<sha256>`), одинаковые файлы хранятся один раз.
- Картинки сжимает и уменьшает клиент до загрузки (до \~1,2 МБ); сервер не тратит процессор на обработку.
- Опционально — внешнее S3-совместимое хранилище для вложений.
- Экран «Адреса и соединение» в админке показывает процессор, память, канал, статус каждого адреса и портов, срок сертификата.

| Настройки | ПК: модальное окно; Android: список → раздел | Шестерёнка | Профиль, внешний вид, голос и видео, уведомления, безопасность и устройства, горячие клавиши (ПК), язык; «Привязать устройство» → привязка | PIN перед фразой и отвязкой (нет макета ввода PIN) |

| Настройки сервера | ПК: модальное окно; Android: список → раздел | Имя сервера, шестерёнка на баннере | Обзор, роли, каналы, участники (все / ожидают / баны), приглашения → создание, модерация, лимиты, адреса | Разделы без прав скрыты; права Владельца заблокированы |
| Создание приглашения | ПК | «Создать приглашение» | Длинная ссылка и «Скопировать», QR, срок, лимит, одобрение, запасные адреса, «Новая ссылка» | «Скопировано» |
| Вход по приглашению | ПК, Android | Ссылка, QR, «+» в рельсе, каталог | Карточка сервера, «Ключ совпадает», адреса, «Вы будете выглядеть так»; «Присоединиться» → «адрес 1 из 3» → готово → главное окно | Ключ не совпал, срок истёк, лимит исчерпан (нет макета) |
| Ключ администратора | ПК, Android | Сервер без владельца | Поле ключа, подсказка `ylsrv admin-token`; «Стать владельцем» → готово → настройки сервера | «Проверяю…»; неверный ключ, лимит попыток (нет макета) |
| Каталог серверов | ПК, Android | Компас | Поиск, теги, «Популярные / Новые / Ближе по пингу»; карточка → панель сервера | «Ничего не нашлось» |
| Панель сервера из каталога | ПК: справа поверх; Android: экран | Карточка в каталоге | Правила, пинг, ключ; «Присоединиться» → вход по приглашению; «Отправить заявку» → «Заявка отправлена»; «Открыть сервер» | Предупреждение 18+; сервер в рельсе со значком «ждёт» (нет макета) |
| Лента | Android | Вкладка «Лента» | Фильтр по серверам, реакции, «Что нового?» и карандаш → новый пост | Пустая лента (нет макета) |
| Новый пост | ПК: модальное окно; Android: лист | «Что нового?», карандаш | Текст, фото или файл, «Где видно»; «Опубликовать» → лента | Сервер с отключёнными стенами недоступен |
| Режим стримера | ПК | Запуск OBS или Streamlabs, Ctrl + Shift + S, настройки | Плашка «Режим стримера» над каналами, «Выкл.» → обычный режим; иконки серверов размыты, название сервера и handle заменены на «скрыто» | Приглашение скрыто, но копируется; уведомления без текста (нет макета) |
| Настройки → Режим стримера | ПК | Раздел в настройках | Автовключение, горячая клавиша, что скрывать: серверы, приглашения и адреса, ключи и handle, текст и звуки уведомлений | — |
| Слэш-команды | ПК, Android | Ввод «/» в поле сообщения | Список команд ботов и встроенных с аргументами и источником; стрелки — выбор, Tab — вставить, Esc — закрыть | Нет совпадений — список скрыт |
| Боты и вебхуки | ПК, Android | Настройки сервера → «Боты и вебхуки» | «Создать бота» → имя и роль → «Создать и показать ключ» → ключ один раз → «Я сохранил ключ»; у бота: включить или выключить, «Роль и права», «Новый ключ»; вебхуки: скопировать, удалить, добавить | Бот не в сети, отключён админом |

Все экраны есть в тёмной теме; светлая нарисована для главного окна ПК и девяти экранов Android, остальные строятся по токенам автоматически.

## Фазы разработки для Claude Code

Двенадцать фаз (0–9 до выпуска, 3б — боты, 10 — модули после MVP), каждая заканчивается работающим срезом, который можно запустить и потрогать; одна фаза — одна или несколько сессий Claude Code с этим документом и нужными макетами в контексте.

Как работать с фазами:

- В корне репозитория лежит `CLAUDE.md`: стек, структура папок, правила (CBOR-кодек только через общий пакет, права считает только сервер, цвета только из токенов), команды сборки и тестов.
- В начале сессии: «Прочитай `docs/spec.md`, раздел N, и макеты `X`, `Y`». Макеты экспортируются с холста как HTML и кладутся в `docs/mockups/`.
- Протокол и криптография — сначала тесты: общие тестовые векторы (`testdata/vectors/*.cbor`) проверяются и в Go, и в Dart.
- Фаза не закрывается, пока не выполнены критерии «Готово, когда».

### Фаза 0. Каркас и инструменты

- [ ] Монорепозиторий: `server/` (Go), `client/` (Flutter), `spec/` (CDDL-схемы CBOR), `docs/`, `testdata/`
- [ ] `CLAUDE.md`, линтеры (`golangci-lint`, `flutter analyze`), CI с тестами на каждый коммит
- [ ] Пакет кодека: CBOR (`fxamacker/cbor` в Go, `cbor` в Dart) + отладочный JSON, утилита `yl-decode`
- [ ] Генератор `YlColors` / `YlText` / `YlSpace` (Dart) из `tokens.json` дизайн-системы, обе темы
- [ ] Базовые виджеты из дизайн-системы: кнопка, переключатель, сегменты, поле, аватар, чип, бейдж, полоса состояния, строка канала

Готово, когда: CI зелёный, витрина виджетов во Flutter показывает все 9 компонентов в тёмной и светлой темах.

### Фаза 1. Идентичность

- [ ] Общая библиотека Go/Dart: BIP39, Ed25519, конверт `Signed`, профиль, `device_cert`, `revoke`, `devices`, отпечатки
- [ ] Тестовые векторы: одна фраза → одинаковые ключи и подписи в обоих языках
- [ ] Хранилище ключей: Android Keystore, Диспетчер учётных данных Windows (DPAPI), libsecret; PIN для главного ключа
- [ ] Экраны онбординга: приветствие, имя и аватар, секретная фраза с подтверждением, восстановление по фразе

Готово, когда: профиль создаётся и восстанавливается по фразе на Windows, Linux и Android; подпись с одной платформы проверяется на другой.

### Фаза 2. Ядро сервера и вход

- [ ] Сервер: конфиг, ключ сервера, SQLite-схема, WebSocket, `hello` → `challenge` → `auth` → `ready`, `resume`
- [ ] `/.well-known/yeenlink`, certmagic, проверка свободных портов при первом запуске
- [ ] Ключ администратора: генерация, `ylsrv admin-token`, `admin.claim`, ограничение попыток
- [ ] Клиент: подключение, экран «Стать владельцем сервера», каркас главного окна (рельса, каналы, чат, участники) и мобильная навигация
- [ ] Пустое состояние «Здесь пока тихо»

Готово, когда: сервер ставится одним бинарником на чистый VPS, клиент входит по ключу и забирает роль Владельца.

### Фаза 3. Текст, роли, профили

- [ ] Каналы и категории, сообщения, история, правки, удаления, реакции, «печатает»
- [ ] Очередь неотправленных (`drift`), дедупликация по `client_id`
- [ ] Вложения: `blob.want` → `PUT /blob`, сжатие картинок на клиенте, лимит размера
- [ ] Права: биты, переопределения, иерархия, `perms.update`; экраны «Роли и права», «Каналы», «Участники»
- [ ] Профиль: `profile.push`, аватар по хешу, список участников с ролями, карточка участника, панель профиля
- [ ] Личные сообщения: список бесед и чат (ПК и Android)

Готово, когда: трое на одном сервере переписываются, роли меняют видимость каналов, сообщения из офлайна доходят без дублей.

### Фаза 3б. Боты

- [ ] Экран «Боты и вебхуки» по макету: список с переключателем, создание с выбором роли, ключ один раз, новый ключ, вебхуки
- [ ] Личность бота: ключ выдаёт сервер, `bot: true` и владелец в профиле, роль «Бот», бейдж «БОТ»
- [ ] Вход бота по тому же WebSocket и challenge; Go SDK
- [ ] Слэш-команды: регистрация, автодополнение в поле ввода, событие `cmd.invoke`
- [ ] Входящие вебхуки `/hook/<секрет>` для одного канала
- [ ] Ограничение частоты: 5 сообщений в секунду на канал, 50 на сервер, ошибка `rate_limited`
- [ ] Бот кубиков на SDK как пример и тест

Готово, когда: бот кубиков отвечает на `/roll` на сервере, его можно ограничить ролью и отключить из админки, а вебхук доставляет сообщение в канал.

### Фаза 4. Приглашения и устойчивость

- [ ] Приглашение: создание (срок, лимит, одобрение, запасные адреса), QR, `invite.redeem`, экран «Вас пригласили» с проверкой ключа
- [ ] Заявки и одобрение новичков, вкладка «Ожидают»
- [ ] Подписанный список адресов, алгоритм переключения, три полосы состояния
- [ ] Экран «Адреса и соединение»: статус адресов, портов, ресурсов

Готово, когда: при блокировке основного адреса (iptables на тестовом сервере) клиент сам уходит на запасной за ≤ 10 с, а сообщения из очереди доходят.

### Фаза 5. Голос

- [ ] LiveKit рядом с сервером (один порт UDP 7882, TCP 7881, TURN по желанию), выдача токенов из прав
- [ ] Голосовой канал: плитки, говорящий, микрофон и звук, выход; блок «Голос подключён» с пингом
- [ ] Мобильный голосовой экран с крупными кнопками
- [ ] Настройки «Голос и видео»: устройства, индикатор, шумо- и эхоподавление, рация

Готово, когда: 10 человек говорят в канале на VPS за 200 ₽ без потерь звука.

### Фаза 6. Демонстрация экрана

- [ ] Окно выбора: экраны, окна, камеры; Wayland через портал
- [ ] Режимы «Игра» и «Текст и код», разрешение до 1440p, кадры до 144, проверка аппаратного кодировщика
- [ ] Лимиты сервера в токене и на сервере; временные слои VP9/AV1
- [ ] Превью «Подключиться к эфиру», режим просмотра, «Покинуть эфир»
- [ ] Монитор канала и деградация 70 / 85 / 95%, полосы для стримера

Готово, когда: стрим 1080p · 60 смотрят 10 человек на 100 Мбит/с, а при искусственной перегрузке срабатывают все три ступени.

### Фаза 7. Настройки и устройства

- [ ] Все разделы настроек пользователя (ПК — модальное окно, Android — список и экраны), включая режим стримера: заглушки, размытие иконок, автовключение по OBS, Ctrl + Shift + S
- [ ] Все разделы настроек сервера, включая лимиты и модерацию (жалобы, журнал)
- [ ] Привязка устройства по QR со стороны старого и нового, подтверждение, отзыв, PIN
- [ ] Нагрузочный тест `lk load-test` и подгонка формулы битрейта

Готово, когда: потерянный ПК отвязывается с телефона и перестаёт входить на все серверы.

### Фаза 8. Стены, лента, каталог

- [ ] Посты: создание (ПК и Android), выбор серверов, реакции, скрытие модератором, лимиты хранения
- [ ] Лента на телефоне, страничка профиля со стеной
- [ ] Сервис каталога (отдельный бинарник): регистрация, heartbeat, проверка ключа, жалобы; клиент — поиск, теги, сортировка по пингу, заявка

Готово, когда: пост с ПК виден в ленте телефона на двух серверах, а публичный сервер находится в каталоге.

### Фаза 9. Светлая тема и выпуск

- [ ] Переключение темы и акцента на лету
- [ ] Сборки: Windows (MSIX или установщик), Linux (AppImage или Flatpak), Android (APK и RuStore)
- [ ] Скрипт установки сервера и короткая документация для админа

* [ ] Пользовательские темы: импорт и экспорт `.yltheme`, проверка контраста перед применением, тема, предложенная сервером

Готово, когда: человек без опыта поднимает сервер по инструкции и приглашает друзей за 15 минут.

### Фаза 10. Модули WebAssembly (после MVP)

- [ ] Среда wazero, формат `manifest.json`, API хоста версии 1
- [ ] Лимиты: 32 МБ памяти, 50 мс на событие, автоотключение после 5 падений
- [ ] Хранилище «ключ–значение» модуля с квотой 10 МБ
- [ ] Установка: хеш, экран запрошенных прав, подтверждение сетевого доступа, журнал модуля
- [ ] SDK для TinyGo и модуль кубиков как пример

Готово, когда: модуль кубиков работает внутри сервера без внешнего процесса, а модуль с бесконечным циклом отключается, не задев сервер и голос.

## Открытые вопросы и риски

| Риск или вопрос | Почему важно | Как снимаем | Фаза |
| --- | --- | --- | --- |
| Захват экрана на Linux Wayland | Основная платформа; портал может ограничить кадры 60 и не дать сетку окон | Прототип захвата через PipeWire в первую неделю фазы 6 | 6 |
| LiveKit без официального .NET — решено переходом на Flutter; но `flutter_webrtc` на Linux | Голос и стримы — ядро продукта | Ранний спайк: голос на Linux в фазе 2 параллельно | 2, 5 |
| Реальный битрейт 1440p · 144 | Формула в интерфейсе — оценка | Нагрузочный тест и подгонка коэффициентов | 7 |
| Утечка seed-фразы | В MVP защиты нет, только новая личность | `next_key_hash` уже в формате; ротация во второй версии | после MVP |
| Реестр ОРИ и публичный каталог | Оператор каталога отвечает за то, что в нём висит | Каталог — отдельный сервис, жалобы и скрытие; размещение официального каталога решить до фазы 8 | 8 |
| Обход бана новым ключом | Ключ создаётся бесплатно | Одобрение новичков, капча, «новые ключи читают сутки» | 3, 7 |
| Лимит трафика на дешёвых VPS | 1–3 ТБ в месяц съедаются стримами | Счётчик месячного трафика в админке и предупреждение | 7 |
| Демонстрация экрана с Android | Не входит в MVP | Решить после выпуска | после MVP |
| Комментарии к постам | Требуют федерации между серверами | Вне MVP, только реакции | после MVP |

Вопросы к решению до старта фазы 0: имя пакета и домен для веб-ссылок приглашений (в документе — `yeenlink.app`), лицензия кода (открытый сервер — да, но какая), и нужна ли зашифрованная копия профиля на родном сервере уже в MVP.
